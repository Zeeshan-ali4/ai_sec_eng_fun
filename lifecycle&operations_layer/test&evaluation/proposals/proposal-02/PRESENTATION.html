AI Security Hackathon · Proposal 02

Safeguarding Adaptive AI

Can you detect controlled data poisoning, preserve useful behavior and recover a local AI assistant before untrusted input becomes trusted knowledge?

Your brief

Measure the change. Defend the learning path.

01

Benchmark

Establish accurate, consistent and safe behavior against a trusted clean reference set.

02

Challenge

Introduce controlled, benign poisoned samples and trace how they influence the assistant.

03

Defend

Apply safeguards, rerun the same tests and demonstrate containment, rollback and residual risk.

Why this matters

Microsoft’s Tay chatbot was manipulated within its first day, showing how fast adversarial public input can reshape system behavior.

The lesson is not to reproduce harmful content. It is to test broadly, layer safeguards, monitor behavior and rehearse rapid intervention.

What you receive

A deliberately weak, fully fictional support assistant.

It can

  • Answer from supplied trusted policies and approved answers
  • Accept proposed answers through a local submission interface
  • Show what was submitted, accepted and retrieved
  • Record source, account, time and resulting behavior
  • Reset between clean and poisoned states

It does not yet defend ingestion well

  • Trusts unverified fictional sources too readily
  • Accepts duplicates without meaningful limits
  • Overweights artificially high ratings
  • Publishes accepted material without quarantine
  • Lacks robust validation and rollback checks

Required challenge set

Six safe poisoning patterns. One traceable system.

A

Rating manipulation

A misleading fictional answer with an artificially high rating.

B

Hidden instruction

An inert instruction requesting only harmless test behavior.

C

Repeated falsehood

A fictional claim repeated to dominate lookup results.

D

Trigger phrase

A benign phrase linked to an intentionally incorrect response.

E

Duplicate amplification

Repeated submissions intended to magnify one untrusted signal.

F

Untrusted correction

A plausible correction from a new fictional account that weakens policy.

What this challenge proves

Strong evidence for one adaptation path, not complete production assurance.

Directly assessed

  • Clean versus poisoned behavior
  • Source trust and provenance
  • Validation and deduplication
  • Quarantine and rollback

Supporting checks

  • Application security for code changes
  • Supply-chain checks for added packages
  • Runtime and model integrity
  • Logs, alerts and response evidence

Separate or later assurance

  • Production-scale monitoring
  • Long-term drift detection
  • Broader fairness evaluation
  • Multiple adaptation mechanisms
Key message: passing the supplied cases shows improved resilience in the authorized scenario. It does not establish production readiness.

Recommended baseline

Use one visible adaptation path: approved answers.

Accepted responses enter a local knowledge base backed by JSON or SQLite. The path is simple enough to understand and rich enough to test trust, duplication, provenance and rollback.

Keep the scope narrow: no model fine-tuning during preparation or the event. Add local RAG only when document poisoning is the central learning objective.
Show who submitted each proposed answer
Show whether it was accepted, quarantined or rejected
Record ratings, duplicates and source trust
Expose which source supported each response
Provide clean and poisoned snapshots
Reset and roll back without rebuilding the environment

Defend the ingestion flow

Do not let acceptance become trust by default.

1

Identify

Capture source, account age and history.

2

Validate

Compare content with trusted policy and schema.

3

Limit

Deduplicate, rate-limit and reduce untrusted influence.

4

Quarantine

Require review before material becomes active.

5

Recover

Detect changes, pause ingestion and roll back.

Evidence standard

Compare the same cases before poisoning, after poisoning and after safeguards.

Accuracy

Did trusted answers change?

Record agreement with the supplied ground truth.

Refusals

Did boundaries weaken?

Track prohibited and unsupported requests consistently.

Consistency

Did repetition dominate?

Compare materially similar prompts and retrieved sources.

Recovery

Can you restore trust?

Demonstrate detection, quarantine, pause and rollback.

Local environment

Designed to run without paid model services.

Ollama runs the approved llama3.1 model locally. A lightweight Python application uses JSON or SQLite for answers, fictional accounts, provenance and logs.

Use only the organizer-supplied model, packages, datasets and installation route. Network access is not required during the event.
Corporate-managed laptop meeting tested hardware requirements

Local browser interface for chat and submissions
Versioned clean and poisoned challenge snapshots
Startup, health-check, reset and rollback instructions
Approximately 7–10 focused working days to prepare the MVP

Non-negotiable boundaries

Weak ingestion. Strong containment.

Use only

  • The isolated challenge environment
  • Fictional support policies
  • Synthetic accounts and submissions
  • Benign labels and placeholders

Never connect

  • Production or corporate systems
  • Real customer or employee data
  • Credentials or confidential records
  • External tools or arbitrary code

Stop and escalate

  • Unexpected external access
  • Secrets or personal data
  • Executable or harmful content
  • Any credible risk beyond the sandbox
